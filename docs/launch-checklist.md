# Launch Checklist

## GitHub Readiness

- [ ] README explains what UpdateSentinel is in the first screen.
- [ ] Quick Start works from a fresh clone.
- [ ] Docker command works.
- [ ] `examples/risky-compose.yml` and `examples/report.md` are present.
- [ ] CONTRIBUTING.md is clear.
- [ ] SECURITY.md avoids email placeholders and warns against sharing secrets.
- [ ] Issue templates exist.
- [ ] License is present.
- [ ] Roadmap is visible.
- [ ] Tests pass.
- [ ] Build passes.
- [ ] Docker build passes.

## Reddit Account Readiness

- [ ] Create account ahead of launch.
- [ ] Comment naturally in r/selfhosted.
- [ ] Do not post the product yet.
- [ ] Do not paste links during warm-up.
- [ ] Build some karma.
- [ ] Target 2-4 weeks of normal participation if possible.
- [ ] Keep launch post humble and useful.

## Hacker News Readiness

- [ ] Create account ahead of launch.
- [ ] Use a `Show HN` title.
- [ ] Link to the GitHub repo.
- [ ] Stay available for technical questions.
- [ ] Do not over-explain or market in the comments.

## Lemmy Readiness

- [ ] Pick relevant self-hosted or open-source communities.
- [ ] Keep the post shorter than Reddit.
- [ ] Link to GitHub.
- [ ] Be ready to answer implementation and privacy questions.

## Dev.to / Medium / Hackernoon Article Checklist

- [ ] Explain the practical update problem before mentioning the tool.
- [ ] Include examples of risky tags.
- [ ] Explain why backups and rollback plans matter.
- [ ] Mention that UpdateSentinel runs locally.
- [ ] Link to GitHub, not a landing page.
- [ ] Avoid sales language.

## Launch-week Schedule

- Day 1: publish GitHub repo and verify README, Docker, and examples.
- Day 2: post Show HN.
- Day 3: post to r/selfhosted if account is ready.
- Day 4: post to Lemmy and X.
- Day 5: publish Dev.to article.
- Day 6: cross-post adapted articles to Medium and Hackernoon.
- Day 7: summarize feedback, triage issues, and update roadmap.

## Post-launch Response Checklist

- [ ] Thank people for useful feedback.
- [ ] Turn repeated questions into README improvements.
- [ ] Label bug reports and feature requests.
- [ ] Prioritize false positives and confusing report output.
- [ ] Avoid arguing about roadmap scope.
- [ ] Keep the MVP read-only unless a future issue explicitly changes that scope.
